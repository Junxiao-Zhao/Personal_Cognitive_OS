# PCO v0.5 Agent-agnostic Workspace Design

> Status: approved design
> Date: 2026-08-30
> Product version: 0.5.0

## 1. Decision

PCO v0.5 is a clean-break, Agent-agnostic personal cognitive memory system. It removes all runtime coupling to OpenCode, Codex, Claude Code, or any other Agent Harness.

The user-facing workflow has two logical permission boundaries:

1. An Agent proposes changes as human-readable Markdown files and input artifacts in an isolated proposal directory. The Host applies its write-permission policy to the Agent Edit and, when supported, shows its diff.
2. The Agent invokes `pco proposal commit <review_id>`. Before PCO appends canonical revisions, the Host applies its write-permission policy to that command.

These are logical boundaries, not a promise that every Host presents exactly two prompts. A Host may split, combine, or omit prompts according to its own sandbox policy. PCO does not capture or claim cryptographic proof that the user saw or accepted final proposal bytes. The Host sandbox configuration is an external deployment trust boundary.

## 2. Goals

- Use one self-contained PCO workspace from any Agent that supports project-local `.agents/skills`, shell commands, and a read-only workspace with one-time write escalation.
- Make every canonical business change visible and editable as Markdown before commit.
- Preserve canonical memory as append-only JSONL in Git.
- Allow several mutually dependent records to commit atomically.
- Keep read, search, validation, and history commands free of filesystem side effects.
- Recover canonical state independently from projections and indexes.
- Make exact evidence attribution and epistemic boundaries validator-enforced.

## 3. Non-goals

- No Harness adapter, plugin, session API, message ID binding, input lock, or Host authorization token.
- No automatic consolidate, idle hook, token threshold, daemon, or background write.
- No compact interception, invocation, audit, or replacement command.
- No full Harness session archive.
- No v0.3 or v0.4 workspace migration or schema compatibility.
- No AFFiNE projection, legacy Markdown projection, canonical relations stream, independent backlinks CLI, or search receipt stream.
- No machine-verifiable claim that a particular TUI approval event occurred.
- No durable recovery state machine or concurrency guarantee for workspace initialization, proposal archival, or derivation.
- No global or shared-root SKILL installation, standalone SKILL export, or Host-specific installation adapter.

## 4. System boundary

```text
Agent-visible material / registered sources
        |
        v
pco-memory: read and recall
        |
        v
pco proposal scaffold: emit proposal controls to stdout
        |
        v
pco-consolidate: author manifest and Markdown proposals
        |
        v
Host Edit diff + first one-time write approval
        |
        v
PCO_PROPOSALS/<review_id>/
        |
        v
pco proposal validate <review_id>
        |
        v
pco proposal commit <review_id> + commit permission boundary
        |
        v
mem-core validation and internal Git worktree transaction
        |
        v
.pco/canonical append-only JSONL + Git
        |
        v
automatic derivation
  - PCO_MEMORY current projection
  - retrieval index with internal reverse-reference map
```

`pco` is the only Agent-facing CLI. `mem-core` remains the internal, Profile-neutral transaction engine. A PCO Profile declares `application_commit_policy: pco_proposal`; the public `mem` console entry point rejects writes to that Profile's business streams, and `pco proposal commit` invokes mem-core through an internal, transaction-scoped application commit capability.

`DIRECT_PCO_STREAM_WRITE_FORBIDDEN` is an application-layer structure and misuse guard. The proposal context, commit receipt, and internal capability are not represented as unforgeable security credentials, so this mechanism does not claim to resist an actor with arbitrary local Python execution. Host filesystem permissions remain the actual security boundary.

Only the mem-core canonical transaction and its Git commit require strong atomicity, locking, and idempotent crash recovery. Proposal archival, `PCO_MEMORY`, retrieval indexes, and workspace-local SKILL files are non-canonical artifacts with their own simple retain, rebuild, or initialization rules; they do not introduce durable journals or recovery state machines.

## 5. Workspace layout

```text
workspace/
|-- .agents/
|   `-- skills/
|       |-- pco-memory/
|       `-- pco-consolidate/
|-- .pco/
|   |-- canonical/       # append-only JSONL, source blobs, and Git repository
|   |   `-- workspace.json
|   |-- indexes/         # replaceable retrieval generations
|   `-- tmp/             # PCO-owned, disposable process temp directories
|-- PCO_MEMORY/          # read-only current-state projection
`-- PCO_PROPOSALS/       # isolated proposal worktrees
```

The workspace is expected to be read-only to the Agent by default. Read-only enforcement belongs to the Host sandbox, not PCO. `PERMISSIONS.md` in the workspace-local SKILL set documents the requirement:

- reads, scaffold generation, and pure validation run without write approval;
- an Agent Edit into `PCO_PROPOSALS` requires one-time write approval;
- commit, init, derive, and abort require write approval;
- a session-wide or permanent write grant is unsupported.

`pco doctor` verifies PCO state and reports the expected permission contract, but cannot prove that a Host will show a TUI prompt or discover project-local SKILLs. A Host that does not load `.agents/skills` from the workspace is outside the v0.5 compatibility contract.

`pco init [PATH]` creates a dedicated PCO workspace at `PATH`, defaulting to the current directory. The target must be nonexistent or empty; PCO never embeds itself into or overwrites an existing nonempty project. Initialization installs both workspace-local SKILLs, creates the PCO directories and canonical Git repository, and generates one immutable `workspace_id` in `.pco/canonical/workspace.json`.

`workspace.json` is created in the canonical Git repository's initial commit and contains at least `workspace_id`, `workspace_format_version`, and `profile_version`. The file and ID are immutable after initialization: they are never regenerated, rewritten during derivation, or replaced when restoring a workspace. Copying or restoring the complete canonical repository preserves the same ID. `pco doctor` returns `WORKSPACE_INTEGRITY_ERROR` if the file is missing, malformed, changed relative to canonical history, or inconsistent with any canonical proposal receipt. The ID is a lightweight canonical identity, not non-canonical recovery state.

Before any workspace write, initialization applies `lstat`/no-follow checks to the final `PATH` component. It accepts only an absent path or an existing empty real directory. A symlink, regular file, FIFO, socket, device, or other special file returns `WORKSPACE_PATH_UNSAFE`; PCO never follows a final symlink into its target. For an existing directory, PCO opens a no-follow directory handle, verifies stable identity, and performs contained relative operations through that handle. A platform that cannot provide equivalent final-component and directory-identity guarantees rejects initialization rather than weakening the contract.

Initialization claims an accepted target by atomically creating its final `.pco/` directory before writing any other entry inside that target. If the target identity changes or `.pco/` appears between the accepted empty-path check and the atomic claim, the loser returns `WORKSPACE_INIT_RACE`, performs no further writes, and never removes the winner's content. A target already nonempty at initial inspection returns `WORKSPACE_NOT_EMPTY`. Initialization has no recovery journal. If the winning process stops after creating only part of a new workspace, it reports that path; the user removes the incomplete workspace and reruns `pco init [PATH]`.

## 6. Canonical data model

### 6.1 Business streams

```text
evidence
sources
events
psychologies
philosophies
archetypes
hypotheses
meta_revisions
session_handoffs
```

`transactions` is an internal mem-core audit ledger, not a human-authored business stream. The proposal commit receipt lives in this ledger, and a business record's `commit_ref` resolves to that receipt.

The following v0.4 concepts do not exist in v0.5:

```text
checkpoints
search_receipts
relations
complete Harness conversation archives
```

### 6.2 Append-only revisions

Every create or revise operation appends a complete record snapshot. It never overwrites an earlier line.

Each revision contains:

- an immutable record ID;
- a monotonically increasing revision;
- `previous_revision` for revisions after the first;
- a non-empty `change_summary` for revisions;
- structured typed metadata;
- normalized `payload.body_markdown`;
- a `commit_ref` pointing to the proposal commit receipt.

Retirement appends a tombstone revision. It does not physically delete canonical history. Retired objects are excluded from current search and projection by default but remain available in historical and change queries.

### 6.3 Markdown mapping

Each proposed business object is one Markdown file with strict YAML frontmatter:

```markdown
---
type: hypothesis
id: hyp_...
base_revision: 2
operation: revise
evidence_refs:
  - evidence:ev_...
confidence: 0.45
change_summary: Narrow the claim after new counter-evidence
---

The human-readable cognitive statement.
```

Mapping rules:

- frontmatter becomes type-specific structured fields;
- the normalized Markdown body becomes `payload.body_markdown`;
- `base_revision` and `operation` are proposal controls, not business payload;
- mem-core generates `revision`, `recorded_at`, and `schema_version`;
- parsing rejects duplicate keys, unknown fields, unsafe YAML types, and invalid references;
- rendering a canonical record recreates semantically identical, byte-normalized Markdown.

## 7. Proposal model

### 7.1 Isolation

At most one active proposal may exist per workspace:

```text
PCO_PROPOSALS/<review_id>/
|-- manifest.json
|-- evidence/
|-- sources/
|-- events/
|-- psychologies/
|-- philosophies/
|-- archetypes/
|-- hypotheses/
|-- inputs/              # non-business source material listed by manifest
|-- META_MEMORY.md
`-- SESSION_HANDOFF.md
```

The proposal directory has Git-worktree semantics but is not a real Git worktree. mem-core continues to use a real internal Git worktree when committing canonical operations.

`manifest.json` identifies the review, workspace format, Profile, canonical base commit, input material, and the exact relative path and operation of every proposed business file. Proposal business files and proposal input artifacts are both user-visible units of review.

### 7.2 Scaffold, authoring, and first permission boundary

`pco proposal scaffold` is a pure read command. It does not create directories or reserve an ID. It reads the current workspace and prints a scaffold to stdout:

```json
{
  "ok": true,
  "manifest": {
    "review_id": "review_...",
    "base_commit": "...",
    "workspace_version": "0.5.0",
    "profile_version": "0.5.0",
    "input_material": [],
    "files": []
  }
}
```

If an active proposal already exists, it returns `PROPOSAL_ALREADY_ACTIVE`. Because scaffold has no side effects, concurrent scaffold calls are not reservations; proposal validation and commit still enforce the single-active-proposal invariant against actual workspace state.

Each `input_material` entry has a stable `material_id` and one of two shapes:

```yaml
input_material:
  - material_id: journal_current
    kind: local_file
    locator: file:///path/to/journal.md
    expected_content_hash: sha256:...
    fidelity: full_source

  - material_id: remote_excerpt_1
    kind: proposal_artifact
    path: inputs/source_1.txt
    expected_content_hash: sha256:...
    fidelity: selected_excerpt
```

`expected_content_hash` is the SHA-256 of PCO-normalized UTF-8 text. It may be absent while a proposal is being authored but is required before commit. For an existing local source, `pco source diff` reports the current normalized hash for the Agent to copy into the manifest. For a new local source, a new proposal artifact, or material without a prior snapshot, `pco proposal validate <review_id>` returns `observed_content_hash` for every material entry. A missing hash returns `INPUT_MATERIAL_HASH_REQUIRED`; a mismatch returns `INPUT_MATERIAL_HASH_MISMATCH` together with both expected and observed values. The Agent adds or corrects the expected hash through an ordinary reviewable Edit, then validates again. Hash calculation is not duplicated in the SKILL.

PCO text normalization is the following byte-level contract:

1. read the source as bytes exactly once;
2. remove one leading UTF-8 BOM byte sequence `EF BB BF`, if present, and reject UTF-16/UTF-32 BOMs;
3. decode with strict UTF-8 and reject NUL code points;
4. preserve Unicode code points exactly, without NFC, NFD, case, or whitespace normalization;
5. replace every CRLF and remaining CR with LF;
6. if the result is non-empty and does not end in LF, append one LF; preserve any additional trailing LF characters;
7. encode as UTF-8 without a BOM and compute `sha256:<lowercase-hex>` over those normalized bytes.

The normalized bytes, not the raw bytes, become the source blob and the input-material hash basis. Material that fails this contract returns `INPUT_MATERIAL_INVALID`.

PCO v0.5 fixes the following resource limits:

```text
MAX_INPUT_MATERIAL_BYTES     = 16 MiB = 16,777,216 bytes
MAX_IMMUTABLE_SNAPSHOT_BYTES = 64 MiB = 67,108,864 bytes
```

The same bounded material reader is used by proposal validation, commit, and `pco source diff`. For every `local_file`, PCO first performs a no-follow metadata check on the final path component and accepts only a regular file. A symlink, FIFO, socket, device, or any other special file is rejected before content read. PCO must open without following the final symlink, verify through the opened handle that the entry is still the same regular file, and recheck stable identity after reading. If the Host platform cannot provide equivalent no-follow and handle-identity guarantees, `local_file` material is rejected as `INPUT_MATERIAL_UNSAFE`. Existing parent-directory resolution remains subject to Host filesystem policy.

Reads are chunked and stop as soon as either the raw or normalized form of one material exceeds 16 MiB. A preliminary reported file size is checked but is never trusted as the only guard, so sparse or growing files cannot bypass the streaming limit. The 64 MiB snapshot budget covers the exact manifest and business Markdown bytes plus the normalized bytes of all local and proposal-artifact input material retained by the immutable snapshot. It is enforced incrementally while material is captured, before further allocation or canonical operation construction. Oversized individual material returns `INPUT_MATERIAL_TOO_LARGE`; an oversized aggregate returns `PROPOSAL_SNAPSHOT_TOO_LARGE`. Large sources must be reduced to a reviewed `selected_excerpt` proposal artifact.

The JSON array order of `input_material` has no business meaning. `material_id` values are unique ASCII identifiers, and digest construction sorts entries by ascending UTF-8 bytes of `material_id`. If cross-material order matters, the ordered material must be represented as one artifact in v0.5 rather than relying on manifest array position.

Remote content obtained through Host-native web tools is written by the Agent beneath `inputs/` in the same Edit as the manifest and business Markdown. It is never hidden in command arguments or mutable external state. A proposed source revision refers to one `material_id`; `content_hash` and `snapshot_ref` are PCO-generated canonical fields and are forbidden in Agent-authored frontmatter.

The Agent:

1. verifies `PCO_MEMORY`;
2. searches canonical memory for existing objects and revisions;
3. runs `pco proposal scaffold`;
4. explains the intended changes;
5. uses its ordinary Edit capability to create the scaffold-derived `manifest.json`, all initial business files, and any proposal input artifacts together, or to modify an existing proposal.

The Host TUI's Edit diff is the first review surface. PCO does not add a separate preview or materialize command.

The user may directly edit proposal files after creation. Any later Agent edit remains subject to the Host's workspace write policy.

### 7.3 Validation and closed proposal set

`pco proposal validate <review_id>` is pure read-only validation. Its result is advisory; commit always validates one immutable snapshot again.

The manifest is the closed proposal set. Business paths in `files` and `proposal_artifact` paths in `input_material` must be normalized, relative paths beneath the active proposal directory. Every business Markdown file and every regular file beneath `inputs/` must be listed exactly once in its corresponding manifest collection. A path cannot appear in both collections. Validation rejects absolute paths, traversal, symlinks, directories, special files, duplicate paths, unknown files, illegal directories, unlisted input artifacts, and a review ID or proposal root mismatch.

There is no partial commit, caller-supplied file enumeration, or persistent proposal index.

### 7.4 Commit permission boundary and immutable snapshot

`pco proposal commit <review_id>` crosses the second logical permission boundary. It first resolves the active and committed proposal paths and checks for the deterministic canonical receipt. An existing matching receipt enters archive-only retry without acquiring the canonical transaction lock, applying stale-base validation, or reading external input. Otherwise the command requires the single active proposal ID to equal `<review_id>`, acquires the canonical transaction lock, repeats the receipt and active-proposal checks, and then:

1. reads and fixes the exact `manifest.json` bytes;
2. enumerates the proposal tree and rejects symlinks, special files, unknown files, illegal directories, or a business/input-artifact set different from the manifest;
3. reads every listed business Markdown file and proposal input artifact exactly once, verifies its final file identity and hash, and rejects a proposal tree that changes while it is being captured;
4. opens each `local_file` input once, reads and normalizes its complete bytes, verifies stable file identity across that read, and compares the result with `expected_content_hash`; a mismatch returns `SOURCE_CHANGED_DURING_SNAPSHOT`;
5. fixes the manifest bytes, business Markdown bytes, proposal input artifact bytes, and normalized local-source bytes as one immutable in-memory snapshot;
6. validates schemas, revisions, evidence rules, input-material references, cross-record references, and the canonical base against only that snapshot;
7. generates source `content_hash` and `snapshot_ref`, computes the workspace-scoped receipt ID and the three digests in dependency order, then translates the snapshot into append-only business and source-blob operations;
8. commits source blobs, source revisions, other business revisions, and the proposal commit receipt in one mem-core transaction;
9. releases the canonical transaction lock.

After canonical success, or immediately on archive-only retry, the command re-enumerates the active proposal with no symlink following and compares its complete proposal-owned closed set, manifest hash, business-file hashes, and proposal-artifact hashes with the canonical receipt. Only an exact match may be atomically renamed to `PCO_PROPOSALS/.committed/<receipt_id>`.

The rename is outside the canonical transaction and cannot roll it back. An existing or newly created receipt always yields `canonical_status: committed`; archival is reported independently as `archive_status: archived | pending | missing | conflict`:

- `archived`: the exact active proposal was renamed, or the matching committed destination already exists while the active path is absent;
- `pending`: the active proposal matches the receipt, but the atomic rename failed;
- `missing`: neither active nor committed path exists; this is a warning and requires no recovery because canonical data is already committed;
- `conflict`: the active proposal no longer matches the receipt, both paths exist, or the committed destination collides with different content. PCO moves or deletes nothing.

The command's success exit status follows `canonical_status`, not archival outcome. `pending`, `missing`, and `conflict` are structured warnings with paths and suggested action; they never repeat or roll back the canonical transaction and do not block derivation. Archive-only retry never rereads external `local_file` inputs. A semantic no-op has no receipt, returns `canonical_status: no_op`, and omits `archive_status`.

Only after the canonical lock is released does the command trigger derivation. No user-supplied commit hash or file list is required. `expected_content_hash` is a freshness precondition for input material, not an Agent-selected canonical `content_hash`; PCO computes all receipt hashes and canonical source fields from the immutable snapshot.

### 7.5 Proposal commit receipt and digest semantics

The canonical proposal commit receipt contains:

```yaml
type: proposal_commit_receipt
receipt_id: commit_...
workspace_id: workspace_...
review_id: review_...
manifest_hash: sha256:...
files:
  - path: hypotheses/hyp_....md
    hash: sha256:...
input_material:
  - material_id: remote_excerpt_1
    kind: proposal_artifact
    path: inputs/source_1.txt
    hash: sha256:...       # normalized material bytes
    file_hash: sha256:...  # exact proposal file bytes
  - material_id: journal_current
    kind: local_file
    locator: file:///path/to/journal.md
    hash: sha256:...
input_digest: sha256:...
proposal_digest: sha256:...
transaction_digest: sha256:...
committed_at: ...
```

`receipt_id` is fixed before operations are built:

```text
receipt_id = "commit_" + hex(sha256(
  "pco-v0.5-proposal-commit\0"
  + frame(workspace_id)
  + frame(review_id)
))
```

`frame(value)` is the UTF-8 value prefixed by its unsigned 64-bit big-endian byte length. The ID is deterministic and workspace-scoped rather than randomly regenerated or persisted in a separate pre-commit write. Every accepted business revision stores `commit_ref: <receipt_id>`.

`manifest_hash`, each business `files[].hash`, and each proposal artifact's `file_hash` cover the exact captured file bytes. Each `input_material[].hash` covers PCO-normalized UTF-8 bytes and therefore equals its verified expected hash and, when the material becomes a source snapshot, the generated source `content_hash`. A `local_file` is external to the proposal tree and therefore has no `file_hash` in the receipt.

The permission mode is fixed by workspace/Profile policy and is not repeated. The proposal base commit remains transaction control state. `transaction_digest` binds that base commit without duplicating it as another receipt field. The resulting Git commit is the Git commit containing this transaction ledger line and is discoverable from repository history rather than self-referenced inside the commit.

The three digests have distinct contracts:

- `input_digest` identifies the material descriptors and normalized bytes captured in the immutable input snapshot. Entries are sorted by ascending UTF-8 bytes of `material_id`. For each entry, PCO encodes the UTF-8 strings `material_id`, `kind`, selector name (`locator` or `path`), selector value, and `fidelity` in that fixed order, followed by the normalized material bytes; every field is framed with an unsigned 64-bit big-endian byte length. SHA-256 is streamed over the domain prefix `pco-input-digest-v0.5\0` and those framed entries. Manifest array order, expected hashes, time, random IDs, the base commit, and Agent-produced cognitive output are excluded. A prior match produces a replay warning only.
- `proposal_digest` covers the type, operation, record ID, base revision, structured business fields, and normalized body of every proposed business object in deterministic path order. It includes business record IDs but excludes timestamps and generated review, receipt, or transaction IDs.
- `transaction_digest` covers `workspace_id`, the canonical base commit, input and proposal digests, manifest hash, deterministic receipt ID, Profile and schema versions, and the normalized prospective business/source operations. Those operations include each business revision's `commit_ref` and each source blob's content hash. The digest excludes exact Markdown formatting already retained in the receipt's file hashes, the proposal commit receipt that will contain it, the Git commit, and generated `recorded_at` or `committed_at` timestamps, avoiding self-reference. This is the v0.5 name for mem-core's transaction fingerprint and is used for canonical idempotent retry and stale/concurrency validation.

The receipt ID is computed before the transaction digest, and the transaction digest is computed before the receipt is appended. The same workspace, `review_id`, semantic snapshot, canonical base, and Profile controls therefore produce the same receipt ID and transaction digest across a canonical crash retry. The same `review_id` in another workspace produces a different receipt ID and transaction digest. Changes limited to Markdown formatting remain visible through the receipt's exact file hashes but do not create a different canonical transaction identity when the parsed business operations are equivalent.

A proposal is a semantic no-op only when the input digest and proposal digest match a prior commit and all targeted current effective records are already equivalent to the proposed result. It then creates no canonical transaction and reports the equivalent existing records. The same input with a different operation set or business content proceeds normally.

## 8. Proposal lifecycle and recovery

- A denied Agent Edit leaves no proposal change.
- A denied commit leaves canonical memory unchanged and keeps the proposal editable.
- Rejection reasons are not automatically recorded.
- `pco proposal abort <review_id>` deletes the proposal without archive or canonical receipt.
- A canonical HEAD change makes the proposal stale. PCO does not auto-rebase cognitive changes.
- A semantic no-op leaves the proposal intact so the user may edit it further or run `pco proposal abort <review_id>`; it never silently discards reviewed files.
- Canonical success remains committed regardless of archival outcome; before rename, PCO rechecks the proposal-owned closed set and every receipt hash.
- `.committed/` is not an active proposal root, so an archived proposal does not occupy the single active proposal slot.
- If canonical commit succeeds but archive status is `pending`, rerunning `pco proposal commit <review_id>` detects the matching receipt before stale-base or external-input validation and retries only the hash check and rename.
- Archive status `missing` is only a warning. Archive status `conflict` leaves every path untouched so the user can preserve changed content without affecting canonical success.
- If commit succeeds but derivation fails, `pco derive all` rebuilds all derivations from the current canonical commit.
- If Git HEAD changes during transaction execution, the transaction fails and the proposal remains.

Committed proposals are retained as transparent, read-only review artifacts, not canonical data or recovery state. PCO never edits a tree beneath `.committed/`. A future space-reclamation command may garbage-collect them, but proposal GC is outside v0.5.

## 9. Evidence and epistemic policy

Evidence frontmatter records at least:

```text
speaker
source_kind
user_authored
fidelity
```

Rules:

- user conversation excerpts may support personal facts;
- assistant content restores context but cannot independently prove user experience, preference, motive, or personality;
- registered material supports personal facts only when explicitly marked user-authored;
- external sources support psychology or philosophy concepts, not facts about the user;
- Agent summaries and interpretations cannot masquerade as user quotations;
- evidence fidelity is one of `selected_excerpt`, `full_user_provided_transcript`, or `registered_source_excerpt`;
- PCO never claims to have archived a complete session unless the user explicitly supplied the complete transcript.

External research uses ordinary source records. A source revision contains locator, title, retrieval time, provider label, optional query context, content hash, `snapshot_ref`, fidelity, and the actually used excerpts. There is no separate search receipt.

The complete normalized source material admitted by that revision is stored as an immutable content-addressed artifact in the same canonical Git commit:

```text
.pco/canonical/source_blobs/<64-lowercase-hex>
```

`snapshot_ref` resolves to that blob, while `content_hash` is `sha256:<same-hex>`. Both fields are generated by PCO from the immutable commit snapshot; Agent-authored values are rejected. The blob write and every business revision that refers to it are part of the same canonical transaction. Identical normalized content reuses the existing blob; revisions never overwrite or delete prior blobs.

For a local `file:` source the snapshot is the complete normalized file captured once during commit, not merely selected excerpts. The manifest's expected hash prevents a file changed after `pco source diff` from being silently admitted. Remote material comes from a manifest-listed artifact beneath `inputs/`; if that artifact contains only selected excerpts, the snapshot faithfully contains only those supplied excerpts and does not claim full-page fidelity.

## 10. Session handoff

`continuation` is renamed to `session_handoff` to clarify its purpose. It records current topics, unanswered questions, active tensions, recent non-long-term decisions, and plausible next directions.

`SESSION_HANDOFF.md` is optional and is generated only when meaningful unfinished context exists. It is a reviewed business record with append-only revisions, not a fifth cognitive category and not Meta-memory.

## 11. Current projection

`PCO_MEMORY` projects every current effective business stream:

```text
PCO_MEMORY/
|-- manifest.json
|-- evidence/
|-- sources/
|-- events/
|-- psychologies/
|-- philosophies/
|-- archetypes/
|-- hypotheses/
|-- META_MEMORY.md
`-- SESSION_HANDOFF.md
```

Its manifest contains the canonical source commit and hashes for all generated files. A SKILL must run `pco verify --path PCO_MEMORY` before reading it.

If the projection is stale, missing, or modified, the Agent uses canonical search fallback. The empty `PCO_MEMORY` directory created by `pco init` is the missing-projection state and may be replaced by the first derivation. PCO never silently imports manual edits from `PCO_MEMORY`. `pco verify --path PCO_MEMORY` prints the exact modified-file list. `pco derive all` refuses to overwrite those files unless the user first copies their intended changes into a proposal or explicitly invokes `pco derive all --discard-modified-projection`. The discard form repeats the conflict list before replacement and requires write permission; it never silently overwrites a modified projection.

## 12. Retrieval and sources

`pco search` is strictly read-only. It uses a matching retrieval generation when available. When the generation is missing, stale, or broken, it performs a bounded canonical fallback and reports derivation status.

Search modes remain:

```text
current
historical
change
pattern
continuity
```

Continuity uses the latest effective session handoff. Pattern search may traverse reverse references, but backlinks are an internal index/projection implementation detail rather than a public capability.

`pco source diff` is read-only and accesses local `file:` sources only. It materializes and normalizes the current complete file, always reports `current_content_hash`, resolves the previous revision's `snapshot_ref`, and returns a real unified diff between the two complete snapshots. A missing or hash-invalid prior blob is an integrity error, not an empty baseline. Remote sources return `refresh_required`; Agents use Host-native web tools to retrieve remote material and write proposed source files and input artifacts.

There is no `pco source add`; new source registrations are ordinary proposal files.

## 13. Derivation

`pco derive all` has exactly two logical outputs:

1. `PCO_MEMORY` current projection;
2. retrieval index, including the internal reverse-reference map.

Legacy Markdown, AFFiNE, context, and independent backlinks projections are removed.

Derivation starts only after the canonical transaction lock has been released. `pco derive all` always builds both outputs from the current canonical HEAD in process-unique directories created with `mkdtemp` beneath PCO-owned `.pco/tmp/`, then validates them before publication. A normal invocation removes only the temporary directories it created. A crash remnant is never resumed or automatically deleted; later invocations create different random directories and leave all pre-existing entries untouched. The command keeps no persistent stage status, attempt record, derivation journal, or recovery state, and concurrent derivation is unsupported.

Immediately before publishing each output, the command rereads canonical HEAD. If HEAD differs from the source commit, or if construction, validation, or publication fails, the command exits non-zero and the next invocation performs another full rebuild in new temporary directories. A crash may leave a missing, old, or mixed set of non-canonical outputs; their embedded source commit and hashes make that detectable, and read paths use canonical fallback until a rebuild succeeds. Canonical success never rolls back for a derivation failure.

## 15. Workspace-local SKILLs and versioning

`pco init [PATH]` installs `pco-memory` and `pco-consolidate` from immutable package resources directly into the new workspace:

```text
PATH/.agents/skills/pco-memory/
PATH/.agents/skills/pco-consolidate/
```

Each directory contains its own `SKILL.md`, supporting resources, manifest, exact SKILL-set version, file hashes, and `requires_pco` compatibility range. The installed set includes Host-neutral `PERMISSIONS.md` guidance and contains no Host-specific permission template or runtime adapter. `pco verify` checks both workspace-local SKILL trees and their self-manifested hashes without modifying them.

The user opens the initialized PCO workspace as the Agent's working directory. Project-local `.agents/skills` discovery is therefore a v0.5 Host compatibility requirement; [Codex scans from the current working directory toward the repository root](https://learn.chatgpt.com/docs/build-skills), and [OpenCode documents project-local Agent Skills](https://opencode.ai/docs/skills/). PCO does not copy files into a home-directory, global, or shared SKILL root. A Host session opened before initialization may need to be restarted or reopened to discover the new SKILLs.

There is no public export, install, refresh, or repair command in v0.5. Workspace-local SKILL files are created only as part of initializing a nonexistent or empty dedicated workspace and are otherwise treated as read-only application files. Initialization never merges with an arbitrary existing project.

The initial `pco==0.5.0` package records exact `0.5.0` versions for:

- PCO Profile;
- workspace format;
- workspace-local SKILL set;
- proposal manifest schema.

Exact equality with the installed Python package is not required. Every PCO package release declares supported ranges for workspace format, Profile, proposal manifest, and SKILL set; every workspace-local SKILL manifest declares its supported PCO package range. The v0.5 compatibility range for each of these contracts is `>=0.5.0,<0.6.0`. `pco doctor` and `pco verify` require all recorded exact versions to fall within the installed package's ranges and the installed package version to fall within both SKILL manifests' `requires_pco` ranges. Thus a compatible `pco==0.5.1` can use an intact `0.5.0` workspace and SKILL set without refresh.

A later compatible package initializes new workspaces with the exact format, Profile, proposal-manifest, and SKILL versions bundled by that package, each still inside the v0.5 ranges. `pco doctor` checks workspace/Profile and SKILL compatibility, `pco verify` additionally checks SKILL file hashes, and proposal validation and commit check the manifest schema version when a proposal exists.

An out-of-range workspace/Profile/proposal-manifest contract returns `WORKSPACE_FORMAT_MISMATCH`; an out-of-range or hash-invalid SKILL tree returns `WORKSPACE_SKILL_INVALID`. Both checks are read-only and never refresh or rewrite the workspace. mem-core retains an independent package version and declares its own supported compatibility range.

## 16. Product behavior

- Consolidation runs only after an explicit user request to organize, save, or update PCO.
- PCO does not inspect token counts or idle state.
- PCO does not invoke, intercept, observe, or audit Host compact.
- A successful commit reports canonical status and each derivation result without making claims about Host context.
- A new Agent session verifies current projections, searches when needed, and can resume the single active proposal.

Required structured failures include:

```text

WORKSPACE_INTEGRITY_ERROR
WORKSPACE_NOT_EMPTY
WORKSPACE_PATH_UNSAFE

WORKSPACE_SKILL_INVALID
PROPOSAL_ALREADY_ACTIVE
PROPOSAL_NOT_FOUND
PROPOSAL_STALE
PROPOSAL_PATH_UNSAFE
PROPOSAL_MANIFEST_MISMATCH
PROPOSAL_CHANGED_DURING_SNAPSHOT
PROPOSAL_SCHEMA_INVALID
PROPOSAL_REFERENCE_INVALID
PROPOSAL_REVISION_CONFLICT
INPUT_MATERIAL_INVALID
INPUT_MATERIAL_UNSAFE
INPUT_MATERIAL_HASH_REQUIRED
INPUT_MATERIAL_HASH_MISMATCH
INPUT_MATERIAL_TOO_LARGE
PROPOSAL_SNAPSHOT_TOO_LARGE
SOURCE_CHANGED_DURING_SNAPSHOT
DIRECT_PCO_STREAM_WRITE_FORBIDDEN
CANONICAL_HEAD_CHANGED
PROJECTION_MODIFIED
SOURCE_SNAPSHOT_INVALID
DERIVATION_FAILED
```

Every error identifies whether canonical memory changed, whether retry is safe, and the exact recovery command when one exists.

Required recovery paths include:

| Condition | Recovery |
| --- | --- |
| Canonical `workspace.json` is missing, changed, or inconsistent with receipts | Restore the complete canonical repository containing its original initial commit. Never generate a replacement workspace ID. |
| Installed package is outside a recorded compatibility range | Install a package version satisfying the reported workspace and SKILL ranges; verification never rewrites the workspace. |
| Initialization target is a symlink, file, or special entry | Choose a nonexistent path or an empty real directory, then rerun `pco init [PATH]`; PCO never follows or replaces the rejected entry. |
| Another process wins workspace initialization | Let the winning initializer finish, inspect its result, and do not retry against that now-nonempty path. |
| Initialization stopped after partially creating a new workspace | Inspect and remove the incomplete path or choose another nonexistent or empty path, then rerun `pco init [PATH]`; PCO never merges with it. |
| Workspace-local SKILL verification fails | Preserve the workspace and reported files. v0.5 performs no automatic repair or overwrite; restore the matching package resources manually before starting an Agent. |
| Canonical commit returns `archive_status: pending` | Rerun `pco proposal commit <review_id>`; the matching receipt permits hash-checked archive-only retry and never appends the transaction again. |
| Canonical commit returns `archive_status: conflict` | Preserve the changed files and follow the reported paths; canonical status remains committed, and PCO moves or deletes nothing. |
| Canonical commit returns `archive_status: missing` | No recovery is required; canonical status remains committed and the missing review artifact is only a warning. |
| Derivation is missing, old, mixed, or failed | Run `pco derive all`; it ignores old temporary remnants and performs a full canonical rebuild in new random directories. |
| `PCO_MEMORY` is locally modified and the edits should be preserved | Run `pco verify --path PCO_MEMORY`, then copy intended changes into a proposal before deriving. |
| `PCO_MEMORY` is locally modified and the edits should be discarded | Inspect the conflict list, then run `pco derive all --discard-modified-projection`; the command repeats the list before replacement. |
| Local input changed after inspection or during commit capture | Run `pco proposal validate <review_id>`, review its `observed_content_hash` and `pco source diff` as applicable, update the proposal manifest through an Agent Edit, then validate again. |
| Input hash is missing or differs during proposal validation | Review `observed_content_hash`, update `expected_content_hash` through an Agent Edit, then rerun `pco proposal validate <review_id>`. |
| Local input is unsafe or material exceeds a size limit | Copy reviewed text into a regular `inputs/` artifact or reduce it to a `selected_excerpt`, update the manifest through an Agent Edit, then rerun `pco proposal validate <review_id>`. |

## 18. Clean break from v0.4

No deployed v0.3 or v0.4 workspace data requires preservation. v0.5 therefore introduces a new workspace without migration, accepted legacy schema versions, legacy streams, uninstall helpers, or dual runtime paths.

The implementation removes OpenCode resources, Harness adapters, CheckpointEngine, automatic thresholds, compact gates, old projections, compatibility tests, and active v0.4 design documents. Git history plus one v0.5 ADR preserves architectural history.

## 19. Verification

Automated verification covers:

- `pco init [PATH]` creation in nonexistent and empty real directories, including empty `.pco/indexes`, `.pco/tmp`, `PCO_PROPOSALS`, and `PCO_MEMORY` directories; rejection without target mutation for final-component symlink, regular-file, FIFO, socket, device, and other special entries; and absence of writes to home-directory, global, or shared SKILL roots;
- competing initializers, with exactly one atomic `.pco/` claim winner and no cleanup or post-loss write by the loser;
- partial-init reporting without automatic cleanup;
- initial-commit creation and immutability of `.pco/canonical/workspace.json`, integrity failures for missing or changed metadata and receipt-ID mismatch, and preservation of `workspace_id` when a complete canonical repository is copied or restored;
- installation and read-only verification of both `.agents/skills` trees, including self-manifested hashes and `>=0.5.0,<0.6.0` package/workspace/Profile/proposal-manifest/SKILL compatibility vectors;
- acceptance of an intact `0.5.0` workspace and SKILL set by compatible package `0.5.1`, plus rejection without mutation at `0.6.0` and for corrupted SKILL files;
- full append-only revisions, history, and tombstones;
- strict Markdown/frontmatter parsing and body round-trip;
- evidence attribution and invalid personal-fact references;
- scaffold output and `PROPOSAL_ALREADY_ACTIVE` behavior without filesystem writes;
- single active proposal, `.committed/` exclusion, stale handling, abort, semantic no-op, replay warning, and archive-only retry;
- distinct input, proposal, and transaction digest semantics, including new output from previously processed input;
- manifest-set completeness for business files and input artifacts, plus traversal, symlink, special-file, unknown-file, illegal-directory, concurrent-tree-change, and root-mismatch rejection;
- exact BOM, UTF-8, Unicode, newline, and trailing-newline normalization vectors;
- validation-provided `observed_content_hash` for new local inputs, proposal artifacts, and material without a prior snapshot;
- single-read local input capture, required/mismatched expected hashes, proposal-artifact hash validation, and rejection of Agent-authored source `content_hash` or `snapshot_ref`;
- material-ID sorting and manifest-array reorder invariance for `input_digest`;
- workspace-scoped deterministic receipt ID and crash-stable canonical transaction digest, including `workspace_id`, `commit_ref`, and exclusion of receipt self-reference and timestamps;
- different receipt/transaction identities for equal review IDs across workspaces, with exact proposal formatting retained by receipt file hashes rather than transaction identity;
- atomic multi-file reference validation;
- rejection of public `mem` writes to a Profile with `application_commit_policy: pco_proposal`, and successful use of the internal application commit capability by `pco proposal commit`;
- post-transaction closed-set and receipt-hash revalidation before atomic rename into `.committed/`, plus archive-only retry without rereading an externally changed `local_file` or repeating the canonical transaction;
- independent `canonical_status: committed` with every `archive_status` value, including a warning-only `missing` result when both proposal paths are absent and no move or deletion for conflicts;
- read-only search and canonical fallback;
- current projection source commit and hash verification;
