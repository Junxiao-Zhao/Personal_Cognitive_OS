# PCO v0.5 Agent-agnostic Workspace Design

> Status: approved design
> Date: 2026-08-30
> Product version: 0.5.0

## 1. Decision

PCO v0.5 is a clean-break, Agent-agnostic personal cognitive memory system. It removes all runtime coupling to OpenCode, Codex, Claude Code, or any other Agent Harness.

The user-facing workflow has two logical permission boundaries:

1. An Agent proposes changes as human-readable Markdown files and input artifacts in an isolated proposal directory. The Host applies its write-permission policy to the Agent Edit and, when supported, shows its diff.
2. The Agent invokes `pco proposal commit <review_id>`. Before PCO appends canonical revisions, the Host applies its write-permission policy to that command.

These are logical boundaries, not a promise that every Host presents exactly two prompts. A Host may split, combine, or omit prompts according to its own sandbox policy. PCO does not capture or claim cryptographic proof that the user saw or accepted final proposal bytes. The Host sandbox configuration is an external deployment trust boundary.

## 2. Goals

- Use the same PCO Core and SKILL bundle from any Agent that supports SKILL instructions, shell commands, and a read-only workspace with one-time write escalation.
- Make every canonical business change visible and editable as Markdown before commit.
- Preserve canonical memory as append-only JSONL in Git.
- Allow several mutually dependent records to commit atomically.
- Keep read, search, validation, and history commands free of filesystem side effects.
- Recover canonical state independently from projections and indexes.
- Make exact evidence attribution and epistemic boundaries validator-enforced.

## 3. Non-goals

- No Harness adapter, plugin, session API, message ID binding, input lock, or Host authorization token.
- No automatic consolidate, idle hook, token threshold, daemon, or background write.
- No compact interception, invocation, audit, or replacement command.
- No full Harness session archive.
- No v0.3 or v0.4 workspace migration or schema compatibility.
- No AFFiNE projection, legacy Markdown projection, canonical relations stream, independent backlinks CLI, or search receipt stream.
- No machine-verifiable claim that a particular TUI approval event occurred.

## 4. System boundary

```text
Agent-visible material / registered sources
        |
        v
pco-memory: read and recall
        |
        v
pco proposal scaffold: emit proposal controls to stdout
        |
        v
pco-consolidate: author manifest and Markdown proposals
        |
        v
Host Edit diff + first one-time write approval
        |
        v
PCO_PROPOSALS/<review_id>/
        |
        v
pco proposal validate <review_id>
        |
        v
pco proposal commit <review_id> + commit permission boundary
        |
        v
mem-core validation and internal Git worktree transaction
        |
        v
.pco/canonical append-only JSONL + Git
        |
        v
automatic derivation
  - PCO_MEMORY current projection
  - retrieval index with internal reverse-reference map
```

`pco` is the only Agent-facing CLI. `mem-core` remains the internal, Profile-neutral transaction engine. A PCO Profile declares `application_commit_policy: pco_proposal`; the public `mem` console entry point rejects writes to that Profile's business streams, and `pco proposal commit` invokes mem-core through an internal, transaction-scoped application commit capability.

`DIRECT_PCO_STREAM_WRITE_FORBIDDEN` is an application-layer structure and misuse guard. The proposal context, commit receipt, and internal capability are not represented as unforgeable security credentials, so this mechanism does not claim to resist an actor with arbitrary local Python execution. Host filesystem permissions remain the actual security boundary.

## 5. Workspace layout

```text
workspace/
|-- .pco/
|   |-- canonical/       # append-only JSONL, source blobs, and Git repository
|   |-- state/           # proposal and derivation coordination state
|   `-- indexes/         # replaceable retrieval generations
|-- PCO_MEMORY/          # read-only current-state projection
`-- PCO_PROPOSALS/       # isolated proposal worktrees
```

The workspace is expected to be read-only to the Agent by default. Read-only enforcement belongs to the Host sandbox, not PCO. `PERMISSIONS.md` in the exported bundle documents the requirement:

- reads, scaffold generation, and pure validation run without write approval;
- an Agent Edit into `PCO_PROPOSALS` requires one-time write approval;
- commit, init, derive, abort, and `pco export --target PATH` require write approval;
- a session-wide or permanent write grant is unsupported.

`pco doctor` verifies PCO state and reports the expected permission contract, but cannot prove that a Host will show a TUI prompt. A misconfigured Host weakens the approval guarantee.

## 6. Canonical data model

### 6.1 Business streams

```text
evidence
sources
events
psychologies
philosophies
archetypes
hypotheses
meta_revisions
session_handoffs
```

`transactions` is an internal mem-core audit ledger, not a human-authored business stream. The proposal commit receipt lives in this ledger, and a business record's `commit_ref` resolves to that receipt.

The following v0.4 concepts do not exist in v0.5:

```text
checkpoints
search_receipts
relations
complete Harness conversation archives
```

### 6.2 Append-only revisions

Every create or revise operation appends a complete record snapshot. It never overwrites an earlier line.

Each revision contains:

- an immutable record ID;
- a monotonically increasing revision;
- `previous_revision` for revisions after the first;
- a non-empty `change_summary` for revisions;
- structured typed metadata;
- normalized `payload.body_markdown`;
- a `commit_ref` pointing to the proposal commit receipt.

Retirement appends a tombstone revision. It does not physically delete canonical history. Retired objects are excluded from current search and projection by default but remain available in historical and change queries.

### 6.3 Markdown mapping

Each proposed business object is one Markdown file with strict YAML frontmatter:

```markdown
---
type: hypothesis
id: hyp_...
base_revision: 2
operation: revise
evidence_refs:
  - evidence:ev_...
confidence: 0.45
change_summary: Narrow the claim after new counter-evidence
---

The human-readable cognitive statement.
```

Mapping rules:

- frontmatter becomes type-specific structured fields;
- the normalized Markdown body becomes `payload.body_markdown`;
- `base_revision` and `operation` are proposal controls, not business payload;
- mem-core generates `revision`, `recorded_at`, and `schema_version`;
- parsing rejects duplicate keys, unknown fields, unsafe YAML types, and invalid references;
- rendering a canonical record recreates semantically identical, byte-normalized Markdown.

## 7. Proposal model

### 7.1 Isolation

At most one active proposal may exist per workspace:

```text
PCO_PROPOSALS/<review_id>/
|-- manifest.json
|-- evidence/
|-- sources/
|-- events/
|-- psychologies/
|-- philosophies/
|-- archetypes/
|-- hypotheses/
|-- inputs/              # non-business source material listed by manifest
|-- META_MEMORY.md
`-- SESSION_HANDOFF.md
```

The proposal directory has Git-worktree semantics but is not a real Git worktree. mem-core continues to use a real internal Git worktree when committing canonical operations.

`manifest.json` identifies the review, workspace format, Profile, canonical base commit, input material, and the exact relative path and operation of every proposed business file. Proposal business files and proposal input artifacts are both user-visible units of review.

### 7.2 Scaffold, authoring, and first permission boundary

`pco proposal scaffold` is a pure read command. It does not create directories or reserve an ID. It reads the current workspace and prints a scaffold to stdout:

```json
{
  "ok": true,
  "manifest": {
    "review_id": "review_...",
    "base_commit": "...",
    "workspace_version": "0.5.0",
    "profile_version": "0.5.0",
    "input_material": [],
    "files": []
  }
}
```

If an active proposal already exists, it returns `PROPOSAL_ALREADY_ACTIVE`. Because scaffold has no side effects, concurrent scaffold calls are not reservations; proposal validation and commit still enforce the single-active-proposal invariant against actual workspace state.

Each `input_material` entry has a stable `material_id` and one of two shapes:

```yaml
input_material:
  - material_id: journal_current
    kind: local_file
    locator: file:///path/to/journal.md
    expected_content_hash: sha256:...
    fidelity: full_source

  - material_id: remote_excerpt_1
    kind: proposal_artifact
    path: inputs/source_1.txt
    expected_content_hash: sha256:...
    fidelity: selected_excerpt
```

`expected_content_hash` is the SHA-256 of PCO-normalized UTF-8 text. It may be absent while a proposal is being authored but is required before commit. For an existing local source, `pco source diff` reports the current normalized hash for the Agent to copy into the manifest. For a new local source, a new proposal artifact, or material without a prior snapshot, `pco proposal validate <review_id>` returns `observed_content_hash` for every material entry. A missing hash returns `INPUT_MATERIAL_HASH_REQUIRED`; a mismatch returns `INPUT_MATERIAL_HASH_MISMATCH` together with both expected and observed values. The Agent adds or corrects the expected hash through an ordinary reviewable Edit, then validates again. Hash calculation is not duplicated in the SKILL.

PCO text normalization is the following byte-level contract:

1. read the source as bytes exactly once;
2. remove one leading UTF-8 BOM byte sequence `EF BB BF`, if present, and reject UTF-16/UTF-32 BOMs;
3. decode with strict UTF-8 and reject NUL code points;
4. preserve Unicode code points exactly, without NFC, NFD, case, or whitespace normalization;
5. replace every CRLF and remaining CR with LF;
6. if the result is non-empty and does not end in LF, append one LF; preserve any additional trailing LF characters;
7. encode as UTF-8 without a BOM and compute `sha256:<lowercase-hex>` over those normalized bytes.

The normalized bytes, not the raw bytes, become the source blob and the input-material hash basis. Material that fails this contract returns `INPUT_MATERIAL_INVALID`.

The JSON array order of `input_material` has no business meaning. `material_id` values are unique ASCII identifiers, and digest construction sorts entries by ascending UTF-8 bytes of `material_id`. If cross-material order matters, the ordered material must be represented as one artifact in v0.5 rather than relying on manifest array position.

Remote content obtained through Host-native web tools is written by the Agent beneath `inputs/` in the same Edit as the manifest and business Markdown. It is never hidden in command arguments or mutable external state. A proposed source revision refers to one `material_id`; `content_hash` and `snapshot_ref` are PCO-generated canonical fields and are forbidden in Agent-authored frontmatter.

The Agent:

1. verifies `PCO_MEMORY`;
2. searches canonical memory for existing objects and revisions;
3. runs `pco proposal scaffold`;
4. explains the intended changes;
5. uses its ordinary Edit capability to create the scaffold-derived `manifest.json`, all initial business files, and any proposal input artifacts together, or to modify an existing proposal.

The Host TUI's Edit diff is the first review surface. PCO does not add a separate preview or materialize command.

The user may directly edit proposal files after creation. Any later Agent edit remains subject to the Host's workspace write policy.

### 7.3 Validation and closed proposal set

`pco proposal validate <review_id>` is pure read-only validation. Its result is advisory; commit always validates one immutable snapshot again.

The manifest is the closed proposal set. Business paths in `files` and `proposal_artifact` paths in `input_material` must be normalized, relative paths beneath the active proposal directory. Every business Markdown file and every regular file beneath `inputs/` must be listed exactly once in its corresponding manifest collection. A path cannot appear in both collections. Validation rejects absolute paths, traversal, symlinks, directories, special files, duplicate paths, unknown files, illegal directories, unlisted input artifacts, and a review ID or proposal root mismatch.

There is no partial commit, caller-supplied file enumeration, or persistent proposal index.

### 7.4 Commit permission boundary and immutable snapshot

`pco proposal commit <review_id>` crosses the second logical permission boundary. Its canonical phase acquires the canonical transaction lock and then:

1. resolves the single active proposal and requires its ID to equal `<review_id>`;
2. handles an already committed matching receipt as cleanup-only recovery using proposal-owned hashes only, before applying ordinary stale-base checks or reading external input;
3. reads and fixes the exact `manifest.json` bytes;
4. enumerates the proposal tree and rejects symlinks, special files, unknown files, illegal directories, or a business/input-artifact set different from the manifest;
5. reads every listed business Markdown file and proposal input artifact exactly once, verifies its final file identity and hash, and rejects a proposal tree that changes while it is being captured;
6. opens each `local_file` input once, reads and normalizes its complete bytes, verifies stable file identity across that read, and compares the result with `expected_content_hash`; a mismatch returns `SOURCE_CHANGED_DURING_SNAPSHOT`;
7. fixes the manifest bytes, business Markdown bytes, proposal input artifact bytes, and normalized local-source bytes as one immutable in-memory snapshot;
8. validates schemas, revisions, evidence rules, input-material references, cross-record references, and the canonical base against only that snapshot;
9. generates source `content_hash` and `snapshot_ref`, computes the receipt ID and three digests, and translates the snapshot into append-only business and source-blob operations;
10. commits source blobs, source revisions, other business revisions, and the proposal commit receipt in one mem-core transaction;
11. removes the proposal or records cleanup recovery state after canonical success;
12. releases the canonical transaction lock.

Only after the canonical lock is released does the command trigger derivation under an independent derivation lock. No user-supplied commit hash or file list is required. `expected_content_hash` is a freshness precondition for input material, not an Agent-selected canonical `content_hash`; PCO computes all receipt hashes and canonical source fields from the immutable snapshot.

### 7.5 Proposal commit receipt and digest semantics

The canonical proposal commit receipt contains:

```yaml
type: proposal_commit_receipt
receipt_id: commit_...
review_id: review_...
manifest_hash: sha256:...
files:
  - path: hypotheses/hyp_....md
    hash: sha256:...
input_material:
  - material_id: remote_excerpt_1
    kind: proposal_artifact
    path: inputs/source_1.txt
    hash: sha256:...
  - material_id: journal_current
    kind: local_file
    locator: file:///path/to/journal.md
    hash: sha256:...
input_digest: sha256:...
proposal_digest: sha256:...
transaction_digest: sha256:...
committed_at: ...
```

`receipt_id` is fixed before operations are built:

```text
receipt_id = "commit_" + hex(sha256("pco-v0.5-proposal-commit\0" + review_id))
```

The hash input is UTF-8. The ID is deterministic rather than randomly regenerated or persisted in a separate pre-commit write. Every accepted business revision stores `commit_ref: <receipt_id>`.

`manifest_hash` and each business `files[].hash` cover the exact captured file bytes. Each `input_material[].hash` covers PCO-normalized UTF-8 bytes and therefore equals its verified expected hash and, when the material becomes a source snapshot, the generated source `content_hash`.

The permission mode is fixed by workspace/Profile policy and is not repeated. The proposal base commit remains transaction control state. `transaction_digest` binds that base commit without duplicating it as another receipt field. The resulting Git commit is the Git commit containing this transaction ledger line and is discoverable from repository history rather than self-referenced inside the commit.

The three digests have distinct contracts:

- `input_digest` identifies the material descriptors and normalized bytes captured in the immutable input snapshot. Entries are sorted by ascending UTF-8 bytes of `material_id`. For each entry, PCO encodes the UTF-8 strings `material_id`, `kind`, selector name (`locator` or `path`), selector value, and `fidelity` in that fixed order, followed by the normalized material bytes; every field is framed with an unsigned 64-bit big-endian byte length. SHA-256 is streamed over the domain prefix `pco-input-digest-v0.5\0` and those framed entries. Manifest array order, expected hashes, time, random IDs, the base commit, and Agent-produced cognitive output are excluded. A prior match produces a replay warning only.
- `proposal_digest` covers the type, operation, record ID, base revision, structured business fields, and normalized body of every proposed business object in deterministic path order. It includes business record IDs but excludes timestamps and generated review, receipt, or transaction IDs.
- `transaction_digest` covers the canonical base commit, input and proposal digests, manifest hash, deterministic receipt ID, Profile and schema versions, and the normalized prospective business/source operations. Those operations include each business revision's `commit_ref` and each source blob's content hash. The digest excludes the proposal commit receipt that will contain it, the Git commit, and generated `recorded_at` or `committed_at` timestamps, avoiding self-reference. This is the v0.5 name for mem-core's transaction fingerprint and is used for idempotent retry and stale/concurrency validation.

The transaction digest is computed before the receipt is appended. The same `review_id`, immutable snapshot, canonical base, and Profile controls therefore produce the same receipt ID and transaction digest across a crash retry.

A proposal is a semantic no-op only when the input digest and proposal digest match a prior commit and all targeted current effective records are already equivalent to the proposed result. It then creates no canonical transaction and reports the equivalent existing records. The same input with a different operation set or business content proceeds normally.

## 8. Proposal lifecycle and recovery

- A denied Agent Edit leaves no proposal change.
- A denied commit leaves canonical memory unchanged and keeps the proposal editable.
- Rejection reasons are not automatically recorded.
- `pco proposal abort <review_id>` deletes the proposal without archive or canonical receipt.
- A canonical HEAD change makes the proposal stale. PCO does not auto-rebase cognitive changes.
- A semantic no-op leaves the proposal intact so the user may edit it further or run `pco proposal abort <review_id>`; it never silently discards reviewed files.
- Canonical success marks the proposal committed and attempts to clear it before derivation; a cleanup failure does not roll back canonical state and enters the recovery path below.
- If commit succeeds but proposal cleanup fails, rerunning `pco proposal commit <review_id>` enters cleanup-only recovery as soon as it finds the matching proposal commit receipt. It compares only proposal-owned bytes recorded by that receipt: `manifest.json`, business Markdown, and manifest-listed `inputs/` artifacts. It does not reread any `local_file` locator, reapply stale-base validation, or invoke another canonical transaction. A later change to an external source therefore cannot block cleanup. If proposal-owned bytes differ, PCO reports those paths and does not delete them; otherwise it removes the proposal and may retry pending derivation only after the canonical lock is released.
- If commit succeeds but derivation fails, `pco derive all` retries only failed or stale derivations against the current canonical commit.
- If Git HEAD changes during transaction execution, the transaction fails and the proposal remains.

## 9. Evidence and epistemic policy

Evidence frontmatter records at least:

```text
speaker
source_kind
user_authored
fidelity
```

Rules:

- user conversation excerpts may support personal facts;
- assistant content restores context but cannot independently prove user experience, preference, motive, or personality;
- registered material supports personal facts only when explicitly marked user-authored;
- external sources support psychology or philosophy concepts, not facts about the user;
- Agent summaries and interpretations cannot masquerade as user quotations;
- evidence fidelity is one of `selected_excerpt`, `full_user_provided_transcript`, or `registered_source_excerpt`;
- PCO never claims to have archived a complete session unless the user explicitly supplied the complete transcript.

External research uses ordinary source records. A source revision contains locator, title, retrieval time, provider label, optional query context, content hash, `snapshot_ref`, fidelity, and the actually used excerpts. There is no separate search receipt.

The complete normalized source material admitted by that revision is stored as an immutable content-addressed artifact in the same canonical Git commit:

```text
.pco/canonical/source_blobs/<64-lowercase-hex>
```

`snapshot_ref` resolves to that blob, while `content_hash` is `sha256:<same-hex>`. Both fields are generated by PCO from the immutable commit snapshot; Agent-authored values are rejected. The blob write and every business revision that refers to it are part of the same canonical transaction. Identical normalized content reuses the existing blob; revisions never overwrite or delete prior blobs.

For a local `file:` source the snapshot is the complete normalized file captured once during commit, not merely selected excerpts. The manifest's expected hash prevents a file changed after `pco source diff` from being silently admitted. Remote material comes from a manifest-listed artifact beneath `inputs/`; if that artifact contains only selected excerpts, the snapshot faithfully contains only those supplied excerpts and does not claim full-page fidelity.

## 10. Session handoff

`continuation` is renamed to `session_handoff` to clarify its purpose. It records current topics, unanswered questions, active tensions, recent non-long-term decisions, and plausible next directions.

`SESSION_HANDOFF.md` is optional and is generated only when meaningful unfinished context exists. It is a reviewed business record with append-only revisions, not a fifth cognitive category and not Meta-memory.

## 11. Current projection

`PCO_MEMORY` projects every current effective business stream:

```text
PCO_MEMORY/
|-- manifest.json
|-- evidence/
|-- sources/
|-- events/
|-- psychologies/
|-- philosophies/
|-- archetypes/
|-- hypotheses/
|-- META_MEMORY.md
`-- SESSION_HANDOFF.md
```

Its manifest contains the canonical source commit and hashes for all generated files. A SKILL must run `pco verify --path PCO_MEMORY` before reading it.

If the projection is stale, missing, or modified, the Agent uses canonical search fallback. PCO never silently imports manual edits from `PCO_MEMORY`. `pco verify --path PCO_MEMORY` prints the exact modified-file list. `pco derive all` refuses to overwrite those files unless the user first copies their intended changes into a proposal or explicitly invokes `pco derive all --discard-modified-projection`. The discard form repeats the conflict list before replacement and requires write permission; it never silently overwrites a modified projection.

## 12. Retrieval and sources

`pco search` is strictly read-only. It uses a matching retrieval generation when available. When the generation is missing, stale, or broken, it performs a bounded canonical fallback and reports derivation status.

Search modes remain:

```text
current
historical
change
pattern
continuity
```

Continuity uses the latest effective session handoff. Pattern search may traverse reverse references, but backlinks are an internal index/projection implementation detail rather than a public capability.

`pco source diff` is read-only and accesses local `file:` sources only. It materializes and normalizes the current complete file, always reports `current_content_hash`, resolves the previous revision's `snapshot_ref`, and returns a real unified diff between the two complete snapshots. A missing or hash-invalid prior blob is an integrity error, not an empty baseline. Remote sources return `refresh_required`; Agents use Host-native web tools to retrieve remote material and write proposed source files and input artifacts.

There is no `pco source add`; new source registrations are ordinary proposal files.

## 13. Derivation

`pco derive all` has exactly two logical outputs:

1. `PCO_MEMORY` current projection;
2. retrieval index, including the internal reverse-reference map.

Legacy Markdown, AFFiNE, context, and independent backlinks projections are removed.

Derivation starts only after the canonical transaction lock has been released. It uses an independent derivation lock, so index or projection construction never extends the canonical critical section. Derivation stages record `pending`, `running`, `completed`, `failed`, `skipped`, or `stale`, together with attempt ID, source commit, timestamps, and structured errors. Independent stages continue after another stage fails. The command exits non-zero if any enabled stage fails.

Every stage builds into a temporary generation identified by its source canonical commit. Immediately before atomic publication it rereads canonical HEAD. If HEAD differs from the source commit, the generation is marked `stale` and cannot replace the current generation. Canonical success never rolls back for a derivation failure.

## 15. SKILL bundle and versioning

`pco-memory` and `pco-consolidate` are exported together as one indivisible bundle:

```text
pco export --target PATH
pco verify --path PATH
```

The bundle includes a manifest, hashes, and Host-neutral `PERMISSIONS.md`. It contains no Host-specific permission templates or runtime adapter.

`pco export --target PATH` is a managed-file export and is never classified as a read-only bundle operation. Its bundle manifest records every PCO-managed payload path and exported hash. The manifest is a reserved PCO control file, is excluded from its own payload map, and carries `manifest_digest`, computed over canonical manifest JSON with that field omitted. Export preflights the entire target before changing any file:

- a nonexistent or empty target is exported normally;
- if a valid prior bundle manifest exists, an old managed file may be replaced only when its current hash still equals the old manifest hash;
- a modified managed file returns `EXPORT_CONFLICT`;
- an existing path not owned by the prior bundle manifest is never overwritten, followed, or deleted, and a collision with a desired bundle path returns `EXPORT_CONFLICT`;
- an obsolete managed file is removed during bundle upgrade only when its current hash still equals the old manifest hash;
- symlinks, special files, unsafe relative paths, and an invalid prior manifest are rejected before mutation.

Export is crash-recoverable through a reserved target journal `.pco-export.pending.json` and workspace staging beneath `.pco/state/export-staging/<export_id>/`:

1. preflight the complete old and new managed sets without mutating the target;
2. write and hash-verify every new payload and the new manifest in workspace staging;
3. atomically publish the pending journal before the first target-file mutation; the journal contains its own self-excluding digest, the old and new manifest digests, and every `create`, `replace`, or `delete` action with its old and new hashes;
4. apply each action idempotently, accepting `absent` or `new_hash` for a create, `old_hash` or `new_hash` for a replacement, and `old_hash` or `absent` for a deletion; any third state is an `EXPORT_CONFLICT` and is never overwritten;
5. publish the new bundle manifest only after all payload actions reach their new state;
6. remove the pending journal and workspace staging after verifying the published manifest and payloads.

If a process crashes after any target mutation, the next `pco export --target PATH` detects the valid journal and completes that recorded export from its staged bytes before considering a newer bundle. A crash after manifest publication but before journal deletion performs verification and cleanup only. `pco verify --path PATH` reports a valid pending journal as `EXPORT_INCOMPLETE` with `pco export --target PATH` as the recovery command. An invalid journal or a target path in neither its recorded old nor new state is `EXPORT_CONFLICT`.

The journal path is reserved only when accompanied by a valid PCO journal; a pre-existing unowned collision is not overwritten. Target payload writes use temporary siblings and atomic rename. v0.5 has no `--force` mode. The user resolves genuine conflicts, chooses an empty target, or preserves modified files elsewhere before rerunning export. Non-PCO files remain untouched throughout recovery, and `pco verify --path PATH` remains side-effect-free.

The following versions are aligned at `0.5.0`:

- PCO Python package;
- PCO Profile;
- workspace format;
- exported SKILL bundle;
- proposal manifest schema.

mem-core retains an independent package version and declares a supported compatibility range.

## 16. Product behavior

- Consolidation runs only after an explicit user request to organize, save, or update PCO.
- PCO does not inspect token counts or idle state.
- PCO does not invoke, intercept, observe, or audit Host compact.
- A successful commit reports canonical status and each derivation result without making claims about Host context.
- A new Agent session verifies current projections, searches when needed, and can resume the single active proposal.

## 17. Error contract

Required structured failures include:

```text
WORKSPACE_FORMAT_MISMATCH
PROPOSAL_ALREADY_ACTIVE
PROPOSAL_NOT_FOUND
PROPOSAL_STALE
PROPOSAL_PATH_UNSAFE
PROPOSAL_MANIFEST_MISMATCH
PROPOSAL_CHANGED_DURING_SNAPSHOT
PROPOSAL_CHANGED_AFTER_COMMIT
PROPOSAL_SCHEMA_INVALID
PROPOSAL_REFERENCE_INVALID
PROPOSAL_REVISION_CONFLICT
INPUT_MATERIAL_INVALID
INPUT_MATERIAL_HASH_REQUIRED
INPUT_MATERIAL_HASH_MISMATCH
SOURCE_CHANGED_DURING_SNAPSHOT
DIRECT_PCO_STREAM_WRITE_FORBIDDEN
CANONICAL_HEAD_CHANGED
PROJECTION_MODIFIED
SOURCE_SNAPSHOT_INVALID
DERIVATION_FAILED
EXPORT_INCOMPLETE
EXPORT_CONFLICT
```

Every error identifies whether canonical memory changed, whether retry is safe, and the exact recovery command when one exists.

Required recovery paths include:

| Condition | Recovery |
| --- | --- |
| Canonical commit succeeded and proposal cleanup failed | Rerun `pco proposal commit <review_id>`; a matching receipt permits cleanup only and never appends the transaction again. |
| Derivation is failed or stale | Run `pco derive all`. |
| `PCO_MEMORY` is locally modified and the edits should be preserved | Run `pco verify --path PCO_MEMORY`, then copy intended changes into a proposal before deriving. |
| `PCO_MEMORY` is locally modified and the edits should be discarded | Inspect the conflict list, then run `pco derive all --discard-modified-projection`; the command repeats the list before replacement. |
| Export lacked Host write permission | Grant one-time write permission and rerun `pco export --target PATH`. |
| Local input changed after inspection or during commit capture | Run `pco proposal validate <review_id>`, review its `observed_content_hash` and `pco source diff` as applicable, update the proposal manifest through an Agent Edit, then validate again. |
| Input hash is missing or differs during proposal validation | Review `observed_content_hash`, update `expected_content_hash` through an Agent Edit, then rerun `pco proposal validate <review_id>`. |
| A valid export journal records an interrupted export | Rerun `pco export --target PATH`; it resumes the journaled old-to-new transition before starting another export. |
| Export target conflicts with managed or non-PCO files | Run `pco verify --path PATH`, preserve or restore the reported files or choose an empty target, then rerun `pco export --target PATH`. |

## 18. Clean break from v0.4

No deployed v0.3 or v0.4 workspace data requires preservation. v0.5 therefore introduces a new workspace without migration, accepted legacy schema versions, legacy streams, uninstall helpers, or dual runtime paths.

The implementation removes OpenCode resources, Harness adapters, CheckpointEngine, automatic thresholds, compact gates, old projections, compatibility tests, and active v0.4 design documents. Git history plus one v0.5 ADR preserves architectural history.
