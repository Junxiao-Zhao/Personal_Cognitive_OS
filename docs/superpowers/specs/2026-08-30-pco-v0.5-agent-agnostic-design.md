# PCO v0.5 Agent-agnostic Workspace Design

> Status: review pending
> Date: 2026-08-30
> Product version: 0.5.0

## 1. Decision

PCO v0.5 is a clean-break, Agent-agnostic personal cognitive memory system. It removes all runtime coupling to OpenCode, Codex, Claude Code, or any other Agent Harness.

The user-facing workflow has two logical permission boundaries:

1. An Agent proposes changes as human-readable Markdown files in an isolated proposal directory. The Host TUI shows the Agent's Edit diff and asks for one-time write permission.
2. The Agent invokes `pco proposal commit <review_id>`. Before PCO appends canonical revisions, the Host applies its write-permission policy to that command.

These are logical boundaries, not a promise that every Host presents exactly two prompts. A Host may split, combine, or omit prompts according to its own sandbox policy. PCO does not capture or claim cryptographic proof that the user saw or accepted final proposal bytes. The Host sandbox configuration is an external deployment trust boundary.

## 2. Goals

- Use the same PCO Core and SKILL bundle from any Agent that supports SKILL instructions, shell commands, and a read-only workspace with one-time write escalation.
- Make every canonical business change visible and editable as Markdown before commit.
- Preserve canonical memory as append-only JSONL in Git.
- Allow several mutually dependent records to commit atomically.
- Keep read, search, validation, and history commands free of filesystem side effects.
- Recover canonical state independently from projections and indexes.
- Make exact evidence attribution and epistemic boundaries validator-enforced.

## 3. Non-goals

- No Harness adapter, plugin, session API, message ID binding, input lock, or Host authorization token.
- No automatic consolidate, idle hook, token threshold, daemon, or background write.
- No compact interception, invocation, audit, or replacement command.
- No full Harness session archive.
- No v0.3 or v0.4 workspace migration or schema compatibility.
- No AFFiNE projection, legacy Markdown projection, canonical relations stream, independent backlinks CLI, or search receipt stream.
- No machine-verifiable claim that a particular TUI approval event occurred.

## 4. System boundary

```text
Agent-visible material / registered sources
        |
        v
pco-memory: read and recall
        |
        v
pco proposal scaffold: emit proposal controls to stdout
        |
        v
pco-consolidate: author manifest and Markdown proposals
        |
        v
Host Edit diff + first one-time write approval
        |
        v
PCO_PROPOSALS/<review_id>/
        |
        v
pco proposal validate <review_id>
        |
        v
pco proposal commit <review_id> + commit permission boundary
        |
        v
mem-core validation and internal Git worktree transaction
        |
        v
.pco/canonical append-only JSONL + Git
        |
        v
automatic derivation
  - PCO_MEMORY current projection
  - retrieval index with internal reverse-reference map
```

`pco` is the only Agent-facing CLI. `mem-core` remains the internal, Profile-neutral transaction engine. A PCO Profile declares `application_commit_policy: pco_proposal`; the public `mem` console entry point rejects writes to that Profile's business streams, and `pco proposal commit` invokes mem-core through an internal, transaction-scoped application commit capability.

`DIRECT_PCO_STREAM_WRITE_FORBIDDEN` is an application-layer structure and misuse guard. The proposal context, commit receipt, and internal capability are not represented as unforgeable security credentials, so this mechanism does not claim to resist an actor with arbitrary local Python execution. Host filesystem permissions remain the actual security boundary.

## 5. Workspace layout

```text
workspace/
|-- .pco/
|   |-- canonical/       # append-only JSONL, source blobs, and Git repository
|   |-- state/           # proposal and derivation coordination state
|   `-- indexes/         # replaceable retrieval generations
|-- PCO_MEMORY/          # read-only current-state projection
`-- PCO_PROPOSALS/       # isolated proposal worktrees
```

The workspace is expected to be read-only to the Agent by default. Read-only enforcement belongs to the Host sandbox, not PCO. `PERMISSIONS.md` in the exported bundle documents the requirement:

- reads, scaffold generation, and pure validation run without write approval;
- an Agent Edit into `PCO_PROPOSALS` requires one-time write approval;
- commit, init, derive, abort, and `pco export --target PATH` require write approval;
- a session-wide or permanent write grant is unsupported.

`pco doctor` verifies PCO state and reports the expected permission contract, but cannot prove that a Host will show a TUI prompt. A misconfigured Host weakens the approval guarantee.

## 6. Canonical data model

### 6.1 Business streams

```text
evidence
sources
events
psychologies
philosophies
archetypes
hypotheses
meta_revisions
session_handoffs
```

`transactions` is an internal mem-core audit ledger, not a human-authored business stream. The proposal commit receipt lives in this ledger, and a business record's `commit_ref` resolves to that receipt.

The following v0.4 concepts do not exist in v0.5:

```text
checkpoints
search_receipts
relations
complete Harness conversation archives
```

### 6.2 Append-only revisions

Every create or revise operation appends a complete record snapshot. It never overwrites an earlier line.

Each revision contains:

- an immutable record ID;
- a monotonically increasing revision;
- `previous_revision` for revisions after the first;
- a non-empty `change_summary` for revisions;
- structured typed metadata;
- normalized `payload.body_markdown`;
- a `commit_ref` pointing to the proposal commit receipt.

Retirement appends a tombstone revision. It does not physically delete canonical history. Retired objects are excluded from current search and projection by default but remain available in historical and change queries.

### 6.3 Markdown mapping

Each proposed business object is one Markdown file with strict YAML frontmatter:

```markdown
---
type: hypothesis
id: hyp_...
base_revision: 2
operation: revise
evidence_refs:
  - evidence:ev_...
confidence: 0.45
change_summary: Narrow the claim after new counter-evidence
---

The human-readable cognitive statement.
```

Mapping rules:

- frontmatter becomes type-specific structured fields;
- the normalized Markdown body becomes `payload.body_markdown`;
- `base_revision` and `operation` are proposal controls, not business payload;
- mem-core generates `revision`, `recorded_at`, and `schema_version`;
- parsing rejects duplicate keys, unknown fields, unsafe YAML types, and invalid references;
- rendering a canonical record recreates semantically identical, byte-normalized Markdown.

## 7. Proposal model

### 7.1 Isolation

At most one active proposal may exist per workspace:

```text
PCO_PROPOSALS/<review_id>/
|-- manifest.json
|-- evidence/
|-- sources/
|-- events/
|-- psychologies/
|-- philosophies/
|-- archetypes/
|-- hypotheses/
|-- META_MEMORY.md
`-- SESSION_HANDOFF.md
```

The proposal directory has Git-worktree semantics but is not a real Git worktree. mem-core continues to use a real internal Git worktree when committing canonical operations.

`manifest.json` identifies the review, workspace format, Profile, canonical base commit, normalized input material, and the exact relative path and operation of every proposed business file. Proposal business files remain the user-visible unit of review.

### 7.2 Scaffold, authoring, and first permission boundary

`pco proposal scaffold` is a pure read command. It does not create directories or reserve an ID. It reads the current workspace and prints a scaffold to stdout:

```json
{
  "ok": true,
  "manifest": {
    "review_id": "review_...",
    "base_commit": "...",
    "workspace_version": "0.5.0",
    "profile_version": "0.5.0",
    "input_material": [],
    "files": []
  }
}
```

If an active proposal already exists, it returns `PROPOSAL_ALREADY_ACTIVE`. Because scaffold has no side effects, concurrent scaffold calls are not reservations; proposal validation and commit still enforce the single-active-proposal invariant against actual workspace state.

The Agent:

1. verifies `PCO_MEMORY`;
2. searches canonical memory for existing objects and revisions;
3. runs `pco proposal scaffold`;
4. explains the intended changes;
5. uses its ordinary Edit capability to create the scaffold-derived `manifest.json` and all initial business files together, or to modify an existing proposal.

The Host TUI's Edit diff is the first review surface. PCO does not add a separate preview or materialize command.

The user may directly edit proposal files after creation. Any later Agent edit remains subject to the Host's workspace write policy.

### 7.3 Validation and closed proposal set

`pco proposal validate <review_id>` is pure read-only validation. Its result is advisory; commit always validates one immutable snapshot again.

The manifest is the closed proposal set. Its paths must be normalized, relative paths beneath the active proposal directory. Every listed path must identify one allowed business Markdown file, and every business file must be listed exactly once. Validation rejects absolute paths, traversal, symlinks, directories, special files, duplicate paths, unknown files, illegal directories, and a review ID or proposal root mismatch.

There is no partial commit, caller-supplied file enumeration, or persistent proposal index.

### 7.4 Commit permission boundary and immutable snapshot

`pco proposal commit <review_id>` crosses the second logical permission boundary. Under the workspace transaction lock, the command:

1. resolves the single active proposal and requires its ID to equal `<review_id>`;
2. reads and fixes the exact `manifest.json` bytes;
3. enumerates the proposal tree and rejects symlinks, special files, unknown files, illegal directories, or a file set different from the manifest;
4. reads every listed business file exactly once and rejects a tree that changes while it is being captured;
5. treats the manifest and business bytes as one immutable in-memory snapshot for all subsequent parsing, validation, hashing, conversion, and commit work;
6. validates schemas, revisions, evidence rules, cross-record references, and the canonical base;
7. computes the input, proposal, and transaction digests;
8. translates Markdown into append-only operations;
9. creates a proposal commit receipt and invokes one mem-core transaction;
10. removes the proposal after canonical success;
11. triggers derivation.

No user-supplied hash or file list is required. PCO computes the manifest and final business-file hashes from the immutable snapshot at commit time.

### 7.5 Proposal commit receipt and digest semantics

The canonical proposal commit receipt contains:

```yaml
type: proposal_commit_receipt
receipt_id: commit_...
review_id: review_...
manifest_hash: sha256:...
files:
  - path: hypotheses/hyp_....md
    hash: sha256:...
input_digest: sha256:...
proposal_digest: sha256:...
transaction_digest: sha256:...
committed_at: ...
```

The permission mode is fixed by workspace/Profile policy and is not repeated. The proposal base commit remains transaction control state. `transaction_digest` binds that base commit without duplicating it as another receipt field. The resulting Git commit is the Git commit containing this transaction ledger line and is discoverable from repository history rather than self-referenced inside the commit. Each accepted business revision stores `commit_ref: <receipt_id>`.

The three digests have distinct contracts:

- `input_digest` identifies normalized input material, such as evidence and source content. It excludes time, random IDs, the base commit, and Agent-produced cognitive output. A prior match produces a replay warning only.
- `proposal_digest` covers the type, operation, record ID, base revision, structured business fields, and normalized body of every proposed business object in deterministic path order. It includes business record IDs but excludes timestamps and generated review, receipt, or transaction IDs.
- `transaction_digest` covers the canonical base commit, proposal digest, manifest hash, Profile and schema versions, and other transaction controls. This is the v0.5 name for mem-core's transaction fingerprint and is used for idempotent retry and stale/concurrency validation.

A proposal is a semantic no-op only when the input digest and proposal digest match a prior commit and all targeted current effective records are already equivalent to the proposed result. It then creates no canonical transaction and reports the equivalent existing records. The same input with a different operation set or business content proceeds normally.

## 8. Proposal lifecycle and recovery

- A denied Agent Edit leaves no proposal change.
- A denied commit leaves canonical memory unchanged and keeps the proposal editable.
- Rejection reasons are not automatically recorded.
- `pco proposal abort <review_id>` deletes the proposal without archive or canonical receipt.
- A canonical HEAD change makes the proposal stale. PCO does not auto-rebase cognitive changes.
- A semantic no-op leaves the proposal intact so the user may edit it further or run `pco proposal abort <review_id>`; it never silently discards reviewed files.
- A successful commit always clears the proposal, even if derivation later fails.
- If commit succeeds but proposal cleanup fails, rerunning `pco proposal commit <review_id>` finds the matching proposal commit receipt and retries cleanup without committing again. Cleanup occurs only when the current manifest and file hashes still match that receipt; otherwise PCO reports the changed paths and does not delete them.
- If commit succeeds but derivation fails, `pco derive all` retries only failed or stale derivations against the current canonical commit.
- If Git HEAD changes during transaction execution, the transaction fails and the proposal remains.

## 9. Evidence and epistemic policy

Evidence frontmatter records at least:

```text
speaker
source_kind
user_authored
fidelity
```

Rules:

- user conversation excerpts may support personal facts;
- assistant content restores context but cannot independently prove user experience, preference, motive, or personality;
- registered material supports personal facts only when explicitly marked user-authored;
- external sources support psychology or philosophy concepts, not facts about the user;
- Agent summaries and interpretations cannot masquerade as user quotations;
- evidence fidelity is one of `selected_excerpt`, `full_user_provided_transcript`, or `registered_source_excerpt`;
- PCO never claims to have archived a complete session unless the user explicitly supplied the complete transcript.

External research uses ordinary source records. A source revision contains locator, title, retrieval time, provider label, optional query context, content hash, `snapshot_ref`, fidelity, and the actually used excerpts. There is no separate search receipt.

The complete normalized source material admitted by that revision is stored as an immutable content-addressed artifact in the same canonical Git commit:

```text
.pco/canonical/source_blobs/<64-lowercase-hex>
```

`snapshot_ref` resolves to that blob, while `content_hash` is `sha256:<same-hex>`. Identical normalized content reuses the existing blob; revisions never overwrite or delete prior blobs. For a local `file:` source the snapshot is the complete normalized file, not merely selected excerpts. Remote material is snapshotted from the complete content supplied to the proposal by the Agent; if only selected excerpts were retrieved, the snapshot faithfully contains only that supplied material and does not claim full-page fidelity.

## 10. Session handoff

`continuation` is renamed to `session_handoff` to clarify its purpose. It records current topics, unanswered questions, active tensions, recent non-long-term decisions, and plausible next directions.

`SESSION_HANDOFF.md` is optional and is generated only when meaningful unfinished context exists. It is a reviewed business record with append-only revisions, not a fifth cognitive category and not Meta-memory.

## 11. Current projection

`PCO_MEMORY` projects every current effective business stream:

```text
PCO_MEMORY/
|-- manifest.json
|-- evidence/
|-- sources/
|-- events/
|-- psychologies/
|-- philosophies/
|-- archetypes/
|-- hypotheses/
|-- META_MEMORY.md
`-- SESSION_HANDOFF.md
```

Its manifest contains the canonical source commit and hashes for all generated files. A SKILL must run `pco verify --path PCO_MEMORY` before reading it.

If the projection is stale, missing, or modified, the Agent uses canonical search fallback. PCO never silently imports manual edits from `PCO_MEMORY`. `pco verify --path PCO_MEMORY` prints the exact modified-file list. `pco derive all` refuses to overwrite those files unless the user first copies their intended changes into a proposal or explicitly invokes `pco derive all --discard-modified-projection`. The discard form repeats the conflict list before replacement and requires write permission; it never silently overwrites a modified projection.

## 12. Retrieval and sources

`pco search` is strictly read-only. It uses a matching retrieval generation when available. When the generation is missing, stale, or broken, it performs a bounded canonical fallback and reports derivation status.

Search modes remain:

```text
current
historical
change
pattern
continuity
```

Continuity uses the latest effective session handoff. Pattern search may traverse reverse references, but backlinks are an internal index/projection implementation detail rather than a public capability.

`pco source diff` is read-only and accesses local `file:` sources only. It materializes and normalizes the current complete file, resolves the previous revision's `snapshot_ref`, and returns a real unified diff between the two complete snapshots. A missing or hash-invalid prior blob is an integrity error, not an empty baseline. Remote sources return `refresh_required`; Agents use Host-native web tools to retrieve remote material and write proposed source files.

There is no `pco source add`; new source registrations are ordinary proposal files.

## 13. Derivation

`pco derive all` has exactly two logical outputs:

1. `PCO_MEMORY` current projection;
2. retrieval index, including the internal reverse-reference map.

Legacy Markdown, AFFiNE, context, and independent backlinks projections are removed.

Derivation stages record `pending`, `running`, `completed`, `failed`, `skipped`, or `stale`, together with attempt ID, source commit, timestamps, and structured errors. Independent stages continue after another stage fails. The command exits non-zero if any enabled stage fails.

Canonical success never rolls back for a derivation failure. If canonical HEAD changes during a build, the generation is stale and cannot replace the current generation.

## 14. Public CLI

```text
pco init
pco doctor
pco export --target PATH
pco verify [--path PATH]

pco search
pco history
pco source diff

pco proposal status
pco proposal scaffold
pco proposal validate <review_id>
pco proposal commit <review_id>
pco proposal abort <review_id>

pco derive all [--discard-modified-projection]
```

`doctor`, `verify`, `search`, `history`, `source diff`, `proposal status`, `proposal scaffold`, and `proposal validate` are read-only. `init`, `proposal commit`, `proposal abort`, `derive all`, and `export --target` write filesystem state and therefore cross a Host write-permission boundary. The public CLI does not contain a direct `mem txn` escape hatch for PCO business streams.

Removed CLI surfaces include:

```text
run
install-opencode
uninstall-opencode
sync
checkpoint
compact
source add
proposal preview
proposal materialize
proposal diff
derive backlinks
derive context
derive projection
```

## 15. SKILL bundle and versioning

`pco-memory` and `pco-consolidate` are exported together as one indivisible bundle:

```text
pco export --target PATH
pco verify --path PATH
```

The bundle includes a manifest, hashes, and Host-neutral `PERMISSIONS.md`. It contains no Host-specific permission templates or runtime adapter.

`pco export --target PATH` writes or replaces files beneath `PATH`; it is never classified as a read-only bundle operation. `pco verify --path PATH` is its side-effect-free verification counterpart.

The following versions are aligned at `0.5.0`:

- PCO Python package;
- PCO Profile;
- workspace format;
- exported SKILL bundle;
- proposal manifest schema.

mem-core retains an independent package version and declares a supported compatibility range.

## 16. Product behavior

- Consolidation runs only after an explicit user request to organize, save, or update PCO.
- PCO does not inspect token counts or idle state.
- PCO does not invoke, intercept, observe, or audit Host compact.
- A successful commit reports canonical status and each derivation result without making claims about Host context.
- A new Agent session verifies current projections, searches when needed, and can resume the single active proposal.

## 17. Error contract

Required structured failures include:

```text
WORKSPACE_FORMAT_MISMATCH
PROPOSAL_ALREADY_ACTIVE
PROPOSAL_NOT_FOUND
PROPOSAL_STALE
PROPOSAL_PATH_UNSAFE
PROPOSAL_MANIFEST_MISMATCH
PROPOSAL_CHANGED_DURING_SNAPSHOT
PROPOSAL_CHANGED_AFTER_COMMIT
PROPOSAL_SCHEMA_INVALID
PROPOSAL_REFERENCE_INVALID
PROPOSAL_REVISION_CONFLICT
DIRECT_PCO_STREAM_WRITE_FORBIDDEN
CANONICAL_HEAD_CHANGED
PROJECTION_MODIFIED
SOURCE_SNAPSHOT_INVALID
DERIVATION_FAILED
```

Every error identifies whether canonical memory changed, whether retry is safe, and the exact recovery command when one exists.

Required recovery paths include:

| Condition | Recovery |
| --- | --- |
| Canonical commit succeeded and proposal cleanup failed | Rerun `pco proposal commit <review_id>`; a matching receipt permits cleanup only and never appends the transaction again. |
| Derivation is failed or stale | Run `pco derive all`. |
| `PCO_MEMORY` is locally modified and the edits should be preserved | Run `pco verify --path PCO_MEMORY`, then copy intended changes into a proposal before deriving. |
| `PCO_MEMORY` is locally modified and the edits should be discarded | Inspect the conflict list, then run `pco derive all --discard-modified-projection`; the command repeats the list before replacement. |
| Export lacked Host write permission | Grant one-time write permission and rerun `pco export --target PATH`. |

## 18. Clean break from v0.4

No deployed v0.3 or v0.4 workspace data requires preservation. v0.5 therefore introduces a new workspace without migration, accepted legacy schema versions, legacy streams, uninstall helpers, or dual runtime paths.

The implementation removes OpenCode resources, Harness adapters, CheckpointEngine, automatic thresholds, compact gates, old projections, compatibility tests, and active v0.4 design documents. Git history plus one v0.5 ADR preserves architectural history.

## 19. Verification

Automated verification covers:

- full append-only revisions, history, and tombstones;
- strict Markdown/frontmatter parsing and body round-trip;
- evidence attribution and invalid personal-fact references;
- scaffold output and `PROPOSAL_ALREADY_ACTIVE` behavior without filesystem writes;
- single active proposal, stale handling, abort, semantic no-op, replay warning, and crash recovery;
- distinct input, proposal, and transaction digest semantics, including new output from previously processed input;
- manifest-set completeness and hash capture, plus traversal, symlink, special-file, unknown-file, illegal-directory, concurrent-tree-change, and root-mismatch rejection;
- atomic multi-file reference validation;
- rejection of public `mem` writes to a Profile with `application_commit_policy: pco_proposal`, and successful use of the internal application commit capability by `pco proposal commit`;
- cleanup after successful canonical commit;
- read-only search and canonical fallback;
- current projection source commit and hash verification;
- independent derivation failures and stale generations;
- content-addressed source snapshot integrity, complete local source diff, and remote refresh signaling;
- explicit modified-projection discard and idempotent cleanup/derivation recovery;
- export's write-permission classification;
- clean wheel installation, resource enumeration, module import, and CLI help;
- absence of Harness, checkpoint, compact, AFFiNE, and legacy projection runtime code.

SKILL evals and real TUI smoke tests verify:

1. read, search, history, verify, and proposal validation do not request write permission;
2. the Agent explains intended changes before Edit and the Host shows the Edit diff;
3. denial of the first write produces no proposal change;
4. denial of commit preserves the proposal and leaves canonical memory unchanged;
5. commit accepts only the complete manifest-bound immutable proposal snapshot and records the manifest hash;
6. the Agent never requests a permanent workspace write grant;
7. canonical commit survives derivation failure;
8. a new Agent session verifies projections and resumes the active proposal;
9. Host-specific prompt counts may vary while both logical permission boundaries remain documented.

Release gates:

```bash
pytest -q
PCO_RUN_MILVUS=1 pytest -q
git diff --check
```

They are supplemented by clean-wheel install/import/CLI smoke tests and at least Codex and OpenCode TUI permission smoke tests using the exported bundle rather than source resources.
